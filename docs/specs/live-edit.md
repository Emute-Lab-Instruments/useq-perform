# Live-Edit Values

> Spec: editor-side machinery for marking literal values in source as live-controllable knobs/toggles/pickers, manipulating them via inline widgets and a dockable panel (with gamepad), persisting their current values across reloads, and committing the final value back into the source. Counterpart to [MAIN.md](MAIN.md).
> See also [code-evaluation.md](code-evaluation.md) (eval lifecycle, soft eval), [editor.md](editor.md) (main-editor surface), [structural-editing.md](structural-editing.md) (Metas, structural ops), [probes.md](probes.md) (precedent for inline widgets registered against a store), [keybindings.md](keybindings.md) (action registry), [gamepad.md](gamepad.md) (input bindings).
> Runtime/compiler counterpart: [../../src-useq/docs/specs/live-edit.md](../../src-useq/docs/specs/live-edit.md). Wire protocol: [../PROTOCOL.md](../PROTOCOL.md) (TBD: `set-live-inputs` message).

---

## 1. Frame

1.1 A **live-edit** is a literal value in the source that the user has marked as manually-settable at runtime via a UI control. The compiler (firmware and WASM) treats the marked value as an external input; the editor pushes new values per UI tick over a dedicated wire-protocol message; no recompilation occurs on knob turns.

1.2 The product use case is the performer who wants to tune a value (multiplier, cutoff, divisor, switch) by feel while the music plays, without the latency of retyping and re-evaluating. Live-edits are the bridge between code-as-source-of-truth and hands-on performance control.

1.3 Live-edits are a main-editor feature. Tutorial playgrounds may opt in. Read-only secondary editors must not register live-edits against the global store.

1.4 Three representations of a live-edit coexist:
- **Source** — a `(live-edit …)` wrapper form in the document text.
- **Widget** — the rendered surface (slider, knob, toggle, picker) the user manipulates.
- **Slot** — the runtime input slot keyed by the wrapper's `:id`, holding the current value.

The **source is the canonical declaration**; the **slot is the canonical current value**; the widget is a view onto the slot.

## 2. Source Surface

2.1 **Wrapper form.** A live-edit appears in source as a wrapper call:

```lisp
(live-edit <seed> :id <string> :min <num> :max <num>
                  [:name <string>] [:options [<keyword> ...]]
                  [:step <num>] [:precision <integer>])
```

- `<seed>` — the original literal the user marked. Frozen at mark-time; never rewritten by knob turns (§6.2). The widget's `:start` value, restored on `liveEdit.resetToSeed`. Must be a literal (number, boolean, or keyword); a `live-edit` form as seed is rejected (§8.1).
- `:id` — a short stable opaque identifier (default 4 chars from a URL-safe alphabet). Generated by the editor at mark-time, baked into source. Identity for persistence, panel display, and runtime slot keying. The string itself is the wire-level identity (no client-side hashing); see [../../src-useq/docs/specs/live-edit.md §3.2](../../src-useq/docs/specs/live-edit.md).
- `:min` / `:max` — value bounds. Auto-inferred at mark-time (§3.4); user-tuneable via widget context menu, panel, or `nav.intoMeta` keyword editing.
- `:name` — optional human-readable display label. Defaults to `unnamed-<id>` in the panel; editable inline.
- `:options` — present only for enum live-edits; vector of keyword choices.
- `:step` — slider step granularity. Defaults derived from `:precision` (§4.5). User-overridable in wrapper or panel.
- `:precision` — number of decimal places displayed. Defaults to `decimals(seed) + 1` (e.g. seed `0.5` → precision `2`). Canonical knob; `:step` derives from it unless explicitly set.

2.2 **Wrapper recognition.** `live-edit` is registered in `structure.builtinWrappers` ([structural-editing.md §6.2](structural-editing.md)). The structural model treats `(live-edit X …)` as the literal `X` (the **host**) carrying a `live-edit` Meta with the keyword args as payload. Unlike holes — which are first-class structural nodes with no host ([structural-editing.md §2.9.6](structural-editing.md)) — a live-edit always decorates an existing literal. Structural ops act on the host literal; the Meta rides along (§2.3).

2.3 **Structural ops compose for free.** Per [structural-editing.md §6.5](structural-editing.md), Metas ride along through every mutation. `slurp`/`raise`/`transpose`/`wrap` operating on a live-edited literal preserve the live-edit Meta on the moved/re-parented node. The user does not need to think about the wrapper.

2.4 **Folding.** `live-edit` Metas are foldable, default folded — the wrapper text is replaced by the inline widget (§4). The global `structure.foldAllWrappers` setting overrides per-kind defaults.

2.5 **Insertion-mode escape.** Pressing `mode.insert` while focused on a live-edit widget reveals the raw `(live-edit …)` text and places the text caret inside the wrapper. This is the path for hand-editing `:min`/`:max`/`:name` faster than via `nav.intoMeta`. Re-entering structural mode re-folds.

2.6 **Type variants.**

2.6.1 **Numeric scalar** — `<seed>` is a number literal. Widget is a slider/knob.
2.6.2 **Boolean** — `<seed>` is `true` or `false`. Widget is a toggle. `:min`/`:max` ignored.
2.6.3 **Keyword (enum)** — `<seed>` is a keyword (`:up`). Requires `:options` (defaults to `[<seed>]` if omitted, with a warning per §8.2). Widget is a picker / discrete cycler.
2.6.4 **Numeric vector element** — wrapped per element: `[(live-edit 1 …) (live-edit 2 …) (live-edit 3 …)]`. Each element is independently identified, valued, and rendered. The bracket pair `[]` itself is not wrapped. See §3.7 for the marking flow.

2.7 **Cell-id and slot-id are different namespaces.** A wrapper `:id` is a string used to key a runtime slot; a cell name is a symbol used in the language environment. `(define foo (live-edit 0.5 :id "foo" …))` is legal and unambiguous — the cell and the slot happen to share a string but are tracked in different tables. Editor and runtime treat them independently.

## 3. Marking and Unmarking

3.1 The action `liveEdit.mark` is a toggle bound in the `liveEdit` action category ([keybindings.md](keybindings.md)). Behaviour depends on context:
- **Structural mode, cursor on a markable leaf literal**: mark/unmark per §3.2/§3.3.
- **Structural mode, cursor on a vector compound**: enter vector-mark sub-mode per §3.7.
- **Insertion mode, text caret near a literal**: walk up the AST from the caret to find the smallest enclosing markable literal; mark/unmark in place. Caret repositions just after the new wrapper or back at the unwrapped literal. User stays in insertion mode.
- **Cursor on an existing `live-edit` wrapper (in either mode)**: unmark per §3.3.
- **Anywhere else**: no-op flash with a console toast ("live-edit not valid here: <reason>").

3.2 **Marking** wraps the literal:
1. Generate a fresh `:id` (default 4-char URL-safe random, retry on collision within the document, and against persisted-but-orphaned ids per §7.3).
2. Infer `:min`/`:max` per §3.4. Infer `:precision` per §2.1.
3. Replace the literal `X` with `(live-edit X :id <id> :min <m> :max <M>)`.
4. Trigger an immediate eval of the enclosing top-level form. The compiler allocates the input slot; on success, the editor registers the widget in the live-edit store.
5. The runtime is initialised to `<seed>` for the new slot via `set-live-inputs` (so widget and runtime agree from frame 1).

3.3 **Unmarking** strips the wrapper, restoring the inner literal:
1. Replace `(live-edit X :id <id> …)` with `X`.
2. Trigger an immediate eval. The compiler frees the slot; the widget vanishes; persisted value enters orphan state (§7.3).

3.4 **Range inference.** At mark-time, `:min`/`:max` are inferred from the seed and its lexical context:

| Seed                                        | Default `:min` | Default `:max`  |
| ------------------------------------------- | -------------- | --------------- |
| `0 ≤ X ≤ 1`                                 | `0`            | `1`             |
| `-1 ≤ X < 0`                                | `-1`           | `0`             |
| Integer X, parent `slow`/`fast`             | `1`            | `max(16, 2X)`   |
| Number X, parent `osc`/`phasor` head        | `20`           | `max(2000, 2X)` |
| Other numeric X > 0                         | `0`            | `2X`            |
| Other numeric X < 0                         | `2X`           | `0`             |
| Other numeric X == 0                        | `0`            | `1`             |
| Boolean / keyword                           | n/a            | n/a             |

Inference is best-effort; the user always has the final say via the keyword args. Future: extensible inference table driven by parent-form recognition (open question §11.2).

3.5 **Where marking is rejected** (no-op flash + console toast):

3.5.1 **Inside `defstate :initial`** — the init runs once, knob turns would do nothing.
3.5.2 **Inside a quoted, syntax-quoted, or unquote form** (`'…`, `` `… ``, `~…`, `~@…`) — the literal isn't being evaluated.
3.5.3 **In an eagerly-consumed top-level position** — a literal directly consumed by a side-effect form whose value is not bound to a name or used in a signal: `(setbpm 120)`, `(useq-play)`, `(settimesig 4 4)`, etc. The authoritative list of eager-consume heads is maintained in [../../src-useq/docs/specs/live-edit.md §3.12](../../src-useq/docs/specs/live-edit.md); the editor mirrors that list for client-side rejection.
3.5.4 **On a non-literal node** — symbols, lists (other than vector compounds — see §3.7), sets, maps. The action requires a leaf literal (number, boolean, keyword) or a vector compound.

3.6 **Top-level binders are allowed.** `(define x 5)`, `let` bindings, `defstate :update` body, lambda/`defn` bodies — the literal flows into a name that may be read in signal context. Marking lifts the bound name to an input load (see [../../src-useq/docs/specs/live-edit.md §3.10](../../src-useq/docs/specs/live-edit.md) for the compiler-side rule). For a literal inside a `defn` body, all callers of the function share the slot; this is intended (one knob, many call sites) but worth noting because it differs from "one knob per call site".

3.7 **Vector marking sub-mode.** When `liveEdit.mark` is pressed on a vector compound:

3.7.1 Editor enters a transient `vector-mark` sub-mode. Each leaf-literal element of the vector receives a "preview marker" — selected (●) or deselected (○) per the setting `liveEdit.vectorMarkDefault: "all" | "none"` (default `"all"`).

3.7.2 Non-literal elements (`(* x 3)`, nested vectors, symbols) are skipped — they cannot be wrapped and show no preview marker.

3.7.3 Within the sub-mode:
- `nav.next` / `nav.prev` move between markable elements.
- `liveEdit.mark` (the same action) toggles the focused element's preview marker.
- `Enter` (or `liveEdit.confirm`, configurable) commits: each ●-marked element is wrapped per §3.2; ○-marked elements are left untouched. One eval fires for the parent form.
- `Esc` (or `liveEdit.cancel`) aborts: the document is unchanged.

3.7.4 If the vector is empty or contains no markable elements, the action is a no-op flash without entering the sub-mode.

3.7.5 Unmarking a vector containing live-edits: pressing `liveEdit.mark` on a vector that has *any* live-edit children enters the same sub-mode with all live-edited elements pre-selected (●); deselecting and confirming unwraps those elements. This is the round-trip for "remove some/all live-edits from this vector."

3.8 **Multi-cursor marking.** With multiple cursors, `liveEdit.mark` applies pointwise per [structural-editing.md §3.5](structural-editing.md). Each cursor's literal is wrapped with a fresh `:id`. One eval fires after all wraps are written.

3.9 **Copy-paste duplicate handling.** When the editor detects a paste (or any text mutation) that introduces a `live-edit` wrapper whose `:id` is already present elsewhere in the document, the editor rewrites the pasted wrapper(s) to fresh `:id`s in the same paste transaction. The persisted value of the original is **not** inherited — different id, different slot, both initialise to `<seed>` (or the persisted value matching the new id, if any). One eval fires after the paste.

## 4. Widget

4.1 The inline widget is a CodeMirror replace decoration that hides the wrapper text and renders a control surface in its place. Width adapts to the surrounding line; height is the line height plus a small overflow allowance.

4.2 **Visual variants:**
- **Numeric scalar** — horizontal slider with current value displayed; knob variant available via setting (§10.4).
- **Boolean** — two-state pill toggle.
- **Keyword (enum)** — segmented picker; cycles via left/right.
- **Numeric vector element** — same as scalar, sized to match its position in the vector.

4.3 **Widget states.** The widget renders one of:
- `uninitialised` — wrapper is in source but no slot exists on the runtime yet (e.g. immediately after page reload, before first eval). Widget is interactive but value writes go only to the persisted table; nothing is sent to the runtime until eval registers the slot. Visually distinguished by a small "⏳" glyph and faded handle. Auto-eval per §6.6 transitions this to `idle`.
- `idle` — slot allocated, no recent change. Default operating state.
- `editing` — the user is actively manipulating the widget (mouse drag, gamepad axis hold, etc.). Subtle highlight; cursor halo brightens.
- `wasm-preview` — slot allocated on WASM only (after a soft eval in `both` mode); value writes land on WASM only. Hardware is not in sync. Badge: "WASM preview only — hardware not synced." Cleared on next normal eval (§6.5).
- `error` — the wrapper failed compile validation (§8.1); widget shows the diagnostic glyph and the value is locked at the seed.
- `runtime-disabled` — runtime mode is `none`, or compile failed on all active runtimes; widget renders read-only with a "no runtime" indicator. Mirror of [probes.md §1.6.3](probes.md).

4.4 **Differs-from-seed indicator.** When the current value differs from `<seed>` (numeric: `|current - seed| > step/2`; boolean/enum: not equal), the widget shows a small tick mark at the seed position on the slider (or a "•" badge for non-slider variants) and the handle is rendered in a "modified" tone. Tapping the tick (or `liveEdit.resetToSeed` action) snaps back to seed. Standard DAW idiom.

4.5 **Step and precision relation.**
- Default: `:precision` is canonical (default `decimals(seed) + 1`); `:step` defaults to `10^-:precision`.
- If both are set explicitly in the wrapper (or via the panel), both are honoured as written — the user is responsible for keeping them coherent.
- Slider drag snaps to `:step`; displayed value renders at `:precision`. With defaults aligned, drag is glitch-free (each snap is one display unit).

4.6 **Manipulation methods.** All bindings produce identical state transitions:
- Mouse / touch — drag the slider, click the toggle, click an enum option.
- Keyboard arrows — left/right (or up/down) step by `:step` (picker-cycle for enums, toggle for booleans).
- Gamepad — focus-follows-cursor (§5.2).

4.7 **No animation on widget value updates from the runtime.** The widget is the master; reading from the slot is for display sync only on first mount and on reload.

## 5. Panel and Gamepad

5.1 **Live-Edit panel.** A dockable panel (alongside the visualisation panel and console — see [overlays.md](overlays.md) for docking rules; defer panel-specific layout to implementation) lists every live-edit currently in the document. Each row shows: `:name` (or fallback `unnamed-<id>`), current value, control (matched to the inline widget's variant but larger), and an axis-binding indicator.

5.2 **Focus-follows-cursor for gamepad.** Whichever live-edit the structural cursor is currently on (or the panel row currently focused) is the gamepad target. The configured axis (default: right stick X for sliders/scalars, A button for booleans, right stick X-as-cycler for enums; full mapping in [gamepad.md](gamepad.md)) drives that live-edit until the cursor moves to another live-edit (or off all live-edits, in which case the axis is idle).

5.3 **Pin extension (deferred).** A `liveEdit.pinToAxis` action that freezes a live-edit to a specific axis until unpinned, freeing the cursor. Allows N hands-off knobs simultaneously. Out of v1; tracked in §11.

5.4 **Panel actions.** Each row exposes:
- `commit` — bake current value back into source (§6).
- `resetToSeed` — restore to the wrapper's `:start` value.
- `rename` — edit `:name`.
- `editRange` — edit `:min`/`:max`/`:step`/`:precision` (and `:options` for enums).
- `unmark` — equivalent to `liveEdit.mark` toggling off (§3.3).

5.5 **Panel-restricted environments.** Tutorial playgrounds opting into live-edits scope their panel to the playground instance only — no cross-playground bleed. Read-only secondary editors render no widgets and contribute no rows.

## 6. Commit and Lifecycle Actions

6.1 **`liveEdit.commit`** (single-action bake-in):
1. Snapshot the current value from the slot.
2. Replace `(live-edit X :id … :min … :max … …)` with the formatted current value (rounded per `:precision`).
3. Trigger an immediate eval. The compiler frees the slot; persisted value enters orphan state (§7.3); widget vanishes.

If multiple cursors target multiple live-edits, commit applies pointwise per [structural-editing.md §3.5](structural-editing.md).

6.2 **`liveEdit.resetToSeed`** restores the slot value to `<seed>` and pushes a `set-live-inputs` update. Source unchanged. Widget reflects the new value immediately.

6.3 **`liveEdit.rename`** opens an inline rename affordance (or panel input) and writes the new `:name` into the wrapper. Triggers a low-priority eval (queued, not immediate) so the runtime sees the new name (display-only on the runtime side, but it appears in diagnostics).

6.4 **`liveEdit.editRange`** opens an inline editor for `:min`/`:max`/`:step`/`:precision` (and `:options`). On save, validates per §8.1, rewrites the wrapper, triggers an immediate eval.

6.5 **Soft-eval interaction.** Soft eval ([code-evaluation.md §1.1](code-evaluation.md)) is WASM-only by definition. When the soft-evaluated code introduces or modifies live-edits:
- Slots are allocated on WASM only. The widgets enter `wasm-preview` state (§4.3).
- Value writes from those widgets are sent only to WASM via `useq_set_live_inputs` (see [../../src-useq/docs/specs/live-edit.md §5.10](../../src-useq/docs/specs/live-edit.md)), not to hardware.
- Pre-existing live-edits (already registered on hardware from a prior normal eval) continue receiving writes on both runtimes.
- A subsequent normal eval (quantised or immediate) registers the new slots on hardware and clears the `wasm-preview` badge. Widgets return to `idle`.

6.6 **Auto-eval on idle.** After a structural change that affects live-edit allocation (mark/unmark/commit/editRange/copy-paste), if no explicit eval has been triggered within `liveEdit.idleEvalMs` (default 1500 ms), the editor auto-evals the affected top-level form to register the slot(s). This drives `uninitialised` widgets to `idle` and ensures persisted values flush to the runtime. Suppressible via setting `liveEdit.autoEvalOnIdle = false` for users who want to control eval timing strictly.

6.7 **All lifecycle actions are atomic** with respect to the eval queue: a commit-in-flight blocks subsequent commits on the same live-edit until the eval round-trips (success or failure).

## 7. Persistence

7.1 **Storage key.** `uSEQ-Perform-Editor-LiveEdits` (per [persistence.md](persistence.md)).

7.2 **Persisted shape:**

```ts
{
  values: Record<string /* :id */, number | boolean | string /* keyword name */>,
  orphans: Record<string /* :id */, { value: ...; orphanedAt: number /* ms epoch */ }>,
  schemaVersion: 1,
}
```

Values are written debounced at 200 ms after the most recent widget change, plus an immediate flush on `commit` / `unmark` / page hide.

7.3 **Reconciliation triggers.** Reconciliation runs in three cases:
- After every successful main-editor eval.
- On document change (debounced ~500 ms) — covers the case where eval is failing repeatedly while the user is editing live-edit wrappers; persisted values still get cleaned up.
- On page load, after the first successful eval (or after `liveEdit.idleEvalMs` if no eval has fired) — restores persisted values.

Each reconciliation walks the document's live-edit wrappers and computes the current `:id` set:
- IDs in both the doc and `values` — value restored, runtime told via `set-live-inputs`.
- IDs in the doc but not in `values` — slot uses `<seed>`, runtime told via `set-live-inputs`.
- IDs in `values` but not in the doc — moved to `orphans` with `orphanedAt = now`. Removed from `values`.
- IDs in `orphans` whose `orphanedAt` is older than `liveEdit.orphanGcHours` (default 24h) — deleted entirely.
- IDs in `orphans` that reappear in the doc (cut/paste recovery) — restored to `values`, removed from `orphans`.

7.4 **`?nosave` honoured** ([url-params.md](url-params.md)): persistence is read-once at boot and writes are suppressed while the param is set.

7.5 **Multi-tab.** Persistence is per-origin; multiple open tabs read/write the same `values` table. Web Serial connects to one tab at a time, so cross-tab live-edit sync is not a real-world concern; last-write-wins per the `localStorage` default. Not deferred; not planned.

## 8. Failure Modes and Diagnostics

8.1 **Compile-time errors** (block the eval; surface as inline diagnostics per [code-evaluation.md §1.6](code-evaluation.md)). Authoritative list lives in the runtime spec ([../../src-useq/docs/specs/live-edit.md §4.1](../../src-useq/docs/specs/live-edit.md)). Editor-relevant cases include:
- `:id` missing.
- `:id` duplicated within the document (the editor's paste handler §3.9 prevents this for routine paste; hand-typed duplicates still error).
- `:min` not less than `:max`.
- `:min`/`:max` non-numeric for a numeric seed.
- Wrapper appears in a rejected position (§3.5) — the editor refuses to mark in those positions, but a hand-typed wrapper is also rejected by the compiler.
- Live-edit form as `<seed>` of another live-edit (`(live-edit (live-edit …) …)`).

8.2 **Compile-time warnings** (eval succeeds; widget renders; warning surfaced in inline diagnostics and console):
- Seed outside `[:min, :max]` — value is clamped on push to the slot. Widget shows a warning glyph.
- `:options` missing for keyword seed — defaults to `[<seed>]`.
- Live-edit on a literal whose enclosing form is unreachable in any signal context — the slot is allocated but never read; warn but do not error.

8.3 **An unhealthy live-edit must not stop the music.** A failed live-edit eval falls back to LKG on the affected output(s) per [MAIN.md §2.1](MAIN.md). Other live-edits in the document remain active and editable.

8.4 **Runtime disconnect.** If the active runtime disconnects mid-session, widgets enter `runtime-disabled` state but retain their values; values continue persisting. On reconnect, the editor re-issues the current `values` table to the runtime in one batched `set-live-inputs` after the next successful eval.

8.5 **Multi-runtime disagreement** (`both` mode). A live-edit may compile on one runtime and not the other. Behaviour: stream values to whichever runtime(s) compiled the slot. The diagnostic is surfaced as in [code-evaluation.md](code-evaluation.md). No fallback magic.

8.6 **Stale persistence shape.** A persisted `values` table from a future schema version is ignored at load, with a console warning. The user is not blocked from booting.

## 9. Performance

9.1 **Wire bandwidth ceiling (hardware).** Web Serial at 115200 baud is ~14 KB/s sustained. A `set-live-inputs` JSON frame for 10 ids is ~150 bytes; at 60 Hz that's ~9 KB/s. At 20 ids and 60 Hz it's ~18 KB/s — over budget. Mitigations applied in order:
- Send only changed values (no polling). The editor maintains a last-sent table and diff-encodes per UI tick.
- When N (active live-edits being manipulated this tick) > 10, throttle UI tick rate to 30 Hz.
- Wire-protocol binary frame (deferred — see [../PROTOCOL.md](../PROTOCOL.md)) is the next mitigation if the JSON ceiling proves real.

9.2 **WASM call cost.** Single batched `useq_set_live_inputs(json_string)` call per UI tick, regardless of N. Boundary crossings are O(1) per tick. JSON parse on the WASM side is negligible at typical N.

9.3 **Editor render cost.** Widgets render via CodeMirror replace decorations. Up to ~50 simultaneous widgets in the visible viewport before render cost becomes noticeable; off-screen widgets are not rendered (CodeMirror viewport-bound).

9.4 **The hot path is the user's UI tick.** Coalescing, diff-encoding, and wire-frame construction happen here; the runtime's per-sample read is O(1) and identical to a hardware input read.

## 10. Settings

Live-edit-related settings live under `liveEdit.*`:

10.1 `liveEdit.commitTriggersEval: "immediate" | "quantised"` — default `"immediate"`. The eval-strategy used by `liveEdit.commit`.

10.2 `liveEdit.idAlphabet: string` — default `"abcdefghjkmnpqrstuvwxyz23456789"` (URL-safe, no easily-confused chars).

10.3 `liveEdit.idLength: number` — default `4`. Increased automatically (with a warning) if collision rate exceeds threshold within a single doc.

10.4 `liveEdit.scalarWidget: "slider" | "knob"` — default `"slider"`. Per-widget override via `:widget` keyword in the wrapper (open question §11.4).

10.5 `liveEdit.orphanGcHours: number` — default `24`. Time-to-live for orphaned persisted values.

10.6 `liveEdit.vectorMarkDefault: "all" | "none"` — default `"all"`. Initial preview-marker state when entering vector-mark sub-mode (§3.7).

10.7 `liveEdit.idleEvalMs: number` — default `1500`. Idle delay before auto-eval registers freshly-introduced slots (§6.6). Set to `0` to disable auto-eval entirely (equivalent to `liveEdit.autoEvalOnIdle = false`).

10.8 `liveEdit.autoEvalOnIdle: boolean` — default `true`. Master switch for §6.6 auto-eval behaviour.

10.9 `liveEdit.uiTickHz: number` — default `60`. UI tick rate for value batching/sending. Auto-throttled to 30 Hz when active-knob count exceeds threshold (§9.1).

## 11. Open / Deferred

11.1 **Cross-tab live-edit sync.** Two tabs editing the same document; one turns a knob; should the other tab's widget update? Currently last-write-wins via `localStorage`; a real-time sync layer is not planned.

11.2 **Extensible range-inference table.** Today the parent-form heuristics (`slow`/`fast`/`osc`/`phasor`) are hardcoded. A future setting `liveEdit.inferenceRules` could let the user (or a snippet pack) declare "for parent head `svf` arg-position 1, default to `[20, 8000]`".

11.3 **Explicit gamepad pin (`liveEdit.pinToAxis`).** Beyond v1's focus-follows-cursor, an action to pin a live-edit to a specific axis until explicitly unpinned. Allows multiple hands-off knobs.

11.4 **Per-widget visual override.** Whether the wrapper accepts a `:widget` keyword (`:slider`/`:knob`/`:vertical-slider`/`:wheel`/...) overriding the global default. Open whether the widget vocabulary is fixed by the editor or extensible.

11.5 **Curve mappings.** Linear is the default. Exponential / log / dB-curve mappings are common in audio control and would need either a `:curve` keyword in the wrapper or per-widget setting.

11.6 **MIDI / OSC binding.** Out of scope for v1 ([MAIN.md §4.5](MAIN.md) — MIDI is excluded from compatibility surface). If MIDI returns as a workflow, live-edits are the natural binding target.

11.7 **History / undo.** Knob movements are not added to the editor's undo stack today. Whether they should be (with debouncing/coalescing) is open. Source mutations from `mark`/`commit`/`unmark`/`editRange` *are* on the undo stack like any other text edit.

11.8 **Inspector / Storybook story.** Widgets should be renderable in isolation per the props-based UI conventions in `CLAUDE.md` (`value`, `min`, `max`, `step`, `precision`, `state`, `onValueChange`, `onCommit` props). Wired adapter pulls from the live-edit store. Not yet specified beyond this note.
